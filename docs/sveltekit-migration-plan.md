# SvelteKit migration plan

Status: implementation plan, not yet implemented. Reviewed 2026-09-12 against the pre-plan application at `c7eff5e`, the current checkout, and the package registry. This replaces the proposed hosting architecture in the first-release handoff once implemented; the existing application and acceptance record remain the current truth until then.

## Outcome and boundaries

Run the personal pi workspace as one SvelteKit application on a loopback-bound Node process. SvelteKit owns HTML rendering, routing, request hooks, development serving, and the production build. The same process owns one pi SDK runtime, configuration service, and SSE feed. Delete the hand-written HTTP/Vite/static server. Preserve the real conversation, inspector, and side-by-side skill/settings workbench as they behave today.

This is a framework migration, not a product redesign. Keep pi's installed authentication, settings, trust, and JSONL sessions as the sources of truth; keep the pinned `@earendil-works/pi-coding-agent` 0.85.1 unless a compatibility check proves an update necessary. Do not introduce a database, hosted deployment, account system, new provider abstraction, or extra pi process. Do not edit Austin's live pi configuration during migration tests.

At the pre-plan clean baseline, `pnpm check`, all 47 tests, and `pnpm build` passed (2026-09-12). `pnpm test` was run again during plan review and passed 47/47, including the five `src/server/http.test.ts` server tests; the sandbox-blocked baseline reported in an external review does not match this checkout. Existing behavior that must survive includes accepted-versus-completed command states, ordered streamed text/thinking/tool evidence, stop/steer, saved-session resume after a server restart, project trust, redaction, skill revision conflicts/undo, and project/global setting precedence.

## Stack decision

- Target the newest stable SvelteKit 2 release available when implementation begins. On 2026-09-12 the npm `latest` tag is **`@sveltejs/kit` 2.70.3**; `3.0.0-next.27` is a prerelease and is excluded. Pair it with `@sveltejs/adapter-node` 5.5.7. Recheck the stable tags and peer ranges immediately before changing the lockfile.
- Use the coherent current Vite toolchain rather than mixing majors: Vite 8.3.0, `@sveltejs/vite-plugin-svelte` 7.3.0, Svelte 5.57.0, and a compatible Vitest (currently 5.0.0). The installed Node 22.23.2 meets Vite 8's `>=22.12.0` range. Keep pnpm and commit its lockfile. Upgrade unrelated app libraries only when compatibility requires it.
- Use `adapter-node`, not `adapter-static` or a serverless adapter. The pi session is process-long and needs local filesystem/tool access. Production starts with `HOST=127.0.0.1 PORT=4317 node build`; development starts Vite/Kit explicitly on `127.0.0.1:4317` with a strict port. Preserve configurable `PORT` and the current `localhost` and `127.0.0.1` browser access.
- Retain **one** typed tRPC API for interactive queries and mutations: its existing validated router and vanilla Svelte client earn their place across the current command/configuration operations. Move that transport from `nodeHTTPRequestHandler` to the Fetch adapter inside a SvelteKit `+server.ts` route. SvelteKit form actions fit page forms, but replacing these commands would require a second validation/client contract with no user-visible gain. SvelteKit remote functions remain experimental in the current documentation. **SSE transport is a blocking early decision, not a requirement to preserve tRPC subscriptions.** Run the dev-and-production spike below before moving the UI or deleting the old server. Keep exactly one selected feed.
- Keep SSR **enabled** for the single workspace page and `prerender = false`. Server load supplies only a redacted, serializable initial snapshot and establishes the local session cookie; the browser hydrates the existing workspace and starts SSE on mount. Do not set `ssr = false` across the app just to carry over the old SPA. The workspace panels are in-place views of one conversation, so do not invent routes for each sidebar section or put absolute project paths into URLs.

Sources: [SvelteKit structure](https://svelte.dev/docs/kit/project-structure), [Node adapter and shutdown](https://svelte.dev/docs/kit/adapter-node), [Kit configuration and CSRF](https://svelte.dev/docs/kit/configuration), [page rendering options](https://svelte.dev/docs/kit/page-options), [server routes](https://svelte.dev/docs/kit/routing), [server hooks](https://svelte.dev/docs/kit/hooks), [server-only modules](https://svelte.dev/docs/kit/server-only-modules), [remote-function status](https://svelte.dev/docs/kit/remote-functions), [tRPC Fetch adapter](https://trpc.io/docs/server/adapters/fetch), and [tRPC SSE link](https://trpc.io/docs/client/links/httpSubscriptionLink). Version numbers above were checked with `npm view` against npm's stable tags, not inferred from older repository notes.

## Target application shape

```text
src/
  app.html                         # SvelteKit HTML template, replaces root index.html
  app.d.ts                         # App.Locals types only if hooks use locals
  hooks.server.ts                  # local request gate, headers, server init/shutdown
  routes/
    +page.server.ts               # cookie/bootstrap and redacted initial snapshot
    +page.svelte                  # workspace composition and document title
    +error.svelte                 # small, non-sensitive load/startup error view
    api/bootstrap/+server.ts      # renew process cookie after a server restart
    api/events/+server.ts         # only if native Kit SSE wins the early check
    trpc/[...trpc]/+server.ts      # tRPC GET/POST via Fetch adapter; SSE if chosen
  lib/
    server/                       # pi runtime, config, router, process services, access policy
    client/                       # components, workspace controller, workbench, tRPC client
    shared/                       # serializable contracts and presentation helpers
svelte.config.js                  # adapter-node; only necessary Kit configuration
vite.config.ts                    # sveltekit() plugin and local dev host/port
tsconfig.json                     # extends generated .svelte-kit/tsconfig.json
.gitignore                        # includes .svelte-kit/ and adapter output
```

Use `$lib/server` (or `.server.ts`) for runtime, config, access policy, and router; never import their values into client code. The client may use a **type-only** `AppRouter` import for tRPC inference. Keep all pi SDK objects and credentials out of load return values and browser bundles. `src/lib/shared` contains only serializable application types. Move existing UI modules with their current responsibilities; avoid a broad component rewrite during the framework cutover. SvelteKit should own the entry point, so remove `src/client/main.ts` and the manual `mount()` call. Bring global CSS and title into the page/layout in the standard Kit way.

The route layout stays deliberately small: one addressable workspace page, one RPC route, one reconnect bootstrap route, and an event route only if native SSE wins. `+page.server.ts` is a read boundary, not a place to open or switch projects. Opening a project remains an explicit validated user command. Omit `+layout.svelte` because there is no shared route shell; add a minimal root `+error.svelte` that explains a failed load without exposing raw pi/config errors. Keep the existing conversation CSS on the page.

Use the ordinary Kit project files, not a Vite SPA hidden inside Kit. `src/app.html` has `%sveltekit.head%` inside `<head>` and `%sveltekit.body%` inside a wrapping element in `<body>`; use `%sveltekit.assets%` for template asset URLs if any. Delete root `index.html` and its manual module script. `vite.config.ts` uses `sveltekit()` from `@sveltejs/kit/vite`, drops the SPA `build.outDir`, and pins dev `host: '127.0.0.1'`, `port: 4317`, and `strictPort: true`. `tsconfig.json` extends `./.svelte-kit/tsconfig.json`; ignore `.svelte-kit/` and the adapter's `build/` output. In `svelte.config.js`, use `adapter-node` with its documented defaults (`out: 'build'`, `precompress: true`, `envPrefix: ''`); only override a default if testing shows a reason. No `src/error.html` unless the static fallback is needed after testing the root error boundary.

## Runtime and request lifecycle

1. A server-only service factory retains the testable construction of `RuntimeService` and `ConfigService`. A process-level owner caches one initialization promise and exposes `getServices()`. Initialize it once through SvelteKit's server `init` hook or an equivalent idempotent server-only bootstrap. Never create an `AgentSession` or `ModelRuntime` on every request or in a universal `load` function. This process singleton is intentional for this one-user app; it is not request/user state.
2. `hooks.server.ts` applies the local access policy before page and API handlers: require an exact loopback Host (including the configured port), reject an Origin that differs from that request's loopback origin, reject `Sec-Fetch-Site: cross-site`, and require the process cookie for RPC/SSE. Continue binding both dev and production listeners to loopback. Apply `nosniff`, `no-referrer`, and frame protection to responses using Kit's hook/configuration; do not add wildcard CORS. Do not treat a cookie alone as authorization to run a mutation. **Static assets and prerendered output bypass SvelteKit's `handle` hook.** That is safe here only because the static surface is the public app bundle/assets, the workspace is not prerendered, and private data/commands/SSE stay in page load and `+server.ts` routes behind the hook. Never place config, sessions, tokens, or generated private data under `static/`.
3. Generate a random local token once per server process. On an accepted workspace page request, `+page.server.ts` sets a host-only `HttpOnly`, `SameSite=Strict`, `Path=/` cookie and returns `runtime.snapshot()` through the existing redacted serialization boundary. Keep the token out of the rendered page. A narrow `GET /api/bootstrap` renews that cookie for an already-open tab after a server restart; it does not open a pi session. The browser can then query `state` and resubscribe. Verify cookie behavior separately for `localhost` and `127.0.0.1`.
4. The `trpc/[...trpc]` route exports `GET` and `POST` and calls `fetchRequestHandler({ endpoint: '/trpc', req: event.request, router, createContext })`. Context receives the cached runtime/config services after the hook has authorized the request. Keep Zod input validation and existing config path/revision checks. Keep the query/mutation client on a relative same-origin URL. The chosen event transport consumes the existing `events` async generator, which sends an authoritative snapshot on subscribe and then pi deltas; disconnect must propagate abort and remove its listener. Remove the unused tRPC subscription procedure/link or native SSE route when the decision is locked.
5. The page receives its initial snapshot as typed `PageData`. Return only the existing redacted, plain snapshot; Kit serializes server `load` data with `devalue`, so test that this exact shape serializes and that no SDK class, function, credential, or session object crosses into HTML. The current `normalizeSnapshot` restores optional properties lost by the **JSON tRPC** wire format. Keep it on that path unless contract tests prove it can be removed; do not apply it blindly to Kit `PageData`. Build a controller instance per rendered page, seeded from the initial snapshot, then connect on mount. In particular, replace `recent = $state(readRecentProjects())` in `workspaceController.svelte.ts` with an identical server/browser initial value and load `pi.recentProjects` after mount. Replace `ProjectRail.svelte`'s `toLocaleString()` during render with a `<time datetime={session.updatedAt}>` whose initial text is deterministic (fixed locale/time zone or ISO); only switch to the browser's local label after hydration. Keep all browser APIs and active SSE construction out of SSR; keep `crypto.randomUUID()` in submit handlers. On SSE reconnect, preserve current session/cursor guards, unsent message and workbench drafts, and the distinction between an accepted command and a completed turn.
6. Preserve pi's existing session storage and the in-memory one-active-session model. A browser refresh may rehydrate from the redacted server snapshot; a **server** restart has no active in-memory session and requires explicit open/resume of a saved pi session. Loading history must not rerun tools. Config edits remain disk writes, not live-agent changes; undo remains process-local.
7. Shut the pi runtime down once, including an active tool and SSE subscribers. `adapter-node` handles HTTP shutdown and emits `sveltekit:shutdown` for async cleanup. Register a single idempotent runtime disposer; arrange prompt cancellation on SIGINT/SIGTERM so a long-lived SSE response does not keep the local process alive until the adapter's timeout. Verify dev hot reload does not orphan a previous SDK session or accumulate signal listeners. Avoid a custom Node HTTP wrapper merely for lifecycle management.

Adapter-node runtime settings are part of the local access boundary. Map `HOST=127.0.0.1` and `PORT=4317` in the production start script (`PORT` remains overridable); bind Kit/Vite dev to the same host and port explicitly. Do not set a fixed `ORIGIN` to one hostname while promising both `localhost` and `127.0.0.1`: let the adapter derive each request origin from its direct Host header, then check that Host against the exact loopback allowlist and configured port. Keep `PROTOCOL_HEADER`, `HOST_HEADER`, `PORT_HEADER`, `ADDRESS_HEADER`, and `XFF_DEPTH` unset because there is no trusted reverse proxy; do not accept forwarded address/host headers as authority. Leave Kit's `csrf.checkOrigin` enabled and `csrf.trustedOrigins` empty, while recognizing that its built-in check covers form submissions, not the JSON tRPC API; the hook must enforce the API's Origin/Fetch-Site policy in both dev and production. Adapter-node defaults `BODY_SIZE_LIMIT` to 512K: measure a representative large prompt and skill-save request against that limit, then set a finite explicit limit if actual use needs more, with a boundary test. Do not disable the limit wholesale.

## Migration sequence

1. **Lock the baseline.** Record current behavior and tests, check that the working tree remains clean, and create an isolated implementation branch/worktree. Inspect the current `App`, controller, workbench, runtime, config service, and HTTP tests before moving files. Do not overwrite concurrent edits.
2. **Establish a real Kit skeleton.** Use the current official SvelteKit TypeScript template in a temporary directory as a configuration reference, then adapt this repository in place. Recheck stable tags and peer ranges before changing the lockfile. Add `@sveltejs/kit` and `adapter-node`, update the compatible Vite/Svelte/Vitest toolchain and lockfile, add `svelte.config.js` and `src/app.html`, switch to `sveltekit()` and generated TypeScript config, ignore `.svelte-kit/`, and replace `dev`, `check`, `build`, and `start` scripts. Confirm a server-rendered page from both Kit dev and `node build` before moving the pi API.
3. **Run the blocking SSE spike and lock the feed.** With a fake event generator and listener count, exercise tRPC SSE through Kit's Fetch `+server.ts` route and native Kit `Response` SSE in both Kit dev and the built `node build` server. Compare initial authoritative snapshot, ordered text/tool events, client abort actually removing the listener, reconnect after process rotation, and SIGINT/SIGTERM exit while SSE is open. Record the behavior and maintenance cost. Choose the single transport and its client URL; remove the losing route/procedure/link. Do not move the workspace controller or remove the existing HTTP server until this gate passes. A direct adapter-only probe is insufficient evidence.
4. **Move the privileged boundary.** Put pi runtime/config/router/service ownership under `$lib/server`; add the server hook, cookie/bootstrap load and endpoint, and tRPC Fetch route. Prove one query and one mutation through Kit, then the chosen SSE feed, in dev and built Node using injected fake services or an isolated temporary pi home. Test both browser hostnames, port changes, origin/CSRF policy, and body-size behavior before swapping the UI client. Delete `src/server/http.ts`, `src/server/index.ts`, and the bespoke static fallback after the Kit boundary passes; do not leave two app servers.
5. **Make the page idiomatic.** Replace manual client entry with `+page.svelte`, pass initial `PageData` into the workspace composition, move browser-only initialization to mount, and keep the conversation/inspector/workbench layout and navigation guards. Fix the recent-project and session-date hydration paths above; verify the rendered HTML and hydrated DOM match. Preserve typed router inference without bundling server values. Keep the existing real-time controller for live state; Kit load is for initial page data, not for each token/tool update.
6. **Reconcile tests, scripts, and documentation.** Replace `src/server/http.test.ts` with focused hook-gate tests (Host, Origin, Fetch-Site, cookie and headers), `+page.server.ts` tests (redacted/devalue-safe snapshot, cookie issuance, both hostnames), and `+server.ts` tests (tRPC query/mutation, chosen SSE ordering, abort removing its listener, reconnect). Exercise the actual built Node server for static-asset bypass, port/host behavior, BODY_SIZE_LIMIT, and shutdown with SSE open. Port `scripts/test-server.ts`, `browser-check.ts`, `browser-flow.ts`, `browser-recovery.ts`, and the opt-in `smoke.ts` to the built `node build` entrypoint with an isolated test agent directory; eliminate imports of `serve()` and old server paths. Update README commands/architecture, AGENTS.md's current-stack instructions, and the active implementation-handoff text in place. Mark earlier acceptance results as historical and add migration-specific evidence; remove superseded standalone-server descriptions instead of leaving two conflicting architectures.
7. **Cut over only after acceptance.** Run `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm test`, and `pnpm build`. Start the actual adapter-node output with `HOST=127.0.0.1 PORT=4317 node build` and verify the browser loop below. Commit only the migration's files and stop for Austin to dogfood; do not proceed into product hardening or deployment work.

## Parallel execution

Use two or three `gpt-5.6-luna` subagents at `max` reasoning for bounded tasks when they shorten the migration. Give each an isolated worktree, explicit file ownership, and a concrete acceptance check. The coordinator owns the shared Kit skeleton, package/lockfile and configuration changes, cross-boundary contracts, the SSE decision, integration, and final verification; agents must not edit those shared files concurrently.

After the skeleton works, one Luna agent runs the blocking dev-and-built-server SSE comparison. In parallel, another can audit the SSR/hydration paths and prepare UI-only fixes; a third can map the HTTP-test and browser-script ports without depending on the chosen feed. The SSE agent reports evidence for both candidates, but the coordinator locks one transport before the controller or old server is cut over. Then split the remaining server boundary, UI migration, and test/script work by disjoint files. Reconcile branches sequentially, remove the losing SSE code, and run the integrated acceptance checks on the combined tree. Do not keep agents busy on speculative cleanup once the real loop is working.

## Acceptance checks

- The only app listener is the Kit Node server; it binds to `127.0.0.1` at the chosen port. Both `http://127.0.0.1:4317` and `http://localhost:4317` load in development and production. Another port works through `PORT` (and a matching dev command). The response is server-rendered and hydrates without console errors or duplicate pi session creation.
- Foreign Host, mismatched Origin, and cross-site requests are rejected in both dev and production, including JSON POSTs that Kit's form-only CSRF check does not cover. RPC and SSE without the local cookie return 401; an accepted page/bootstrap response issues the cookie. No credential, raw SDK session, or secret-bearing config is serialized into HTML, tRPC responses, or logs. Static assets are served by Kit/adapter, bypass the hook, and contain public assets only; there is no app-maintained filesystem routing.
- Real prompt → pi SDK → streamed text/thinking/tool args/results → transcript/inspector works. An HTTP `accepted` result is separate from final completion. Stop/steer, extension dialogs, and source/trust evidence retain current meaning. SSE disconnect/reconnect sends a fresh authoritative snapshot without replaying tools or leaking listeners.
- A page refresh preserves the active process session. A server restart rotates the cookie, leaves drafts readable, and makes the old active session stale until explicitly resumed from pi's saved history. Project switching and workbench closing still guard unsent/unsaved work.
- A saved skill revision is previewed, saved with conflict handling, and actually loaded in a fresh trusted pi session; scoped defaults do not mutate global settings unexpectedly. The manual real-provider run uses temporary settings/trust/session directories and compares Austin's actual global settings before/after without copying them into the repository.
- Desktop and half-window layouts retain the current conversation/inspector/workbench interaction. Recent projects and session timestamps render without hydration warnings. The browser bundle contains no pi SDK, Node built-ins, auth data, or server implementation values. Production startup and SIGINT/SIGTERM exit cleanly even with SSE open or a tool running.

The transport decision is intentionally narrow. A direct probe against the currently installed tRPC Fetch adapter returned `text/event-stream` and released the generator on cancellation, but it did not run through SvelteKit. The blocking dev-and-production Kit spike decides whether tRPC SSE or a native streamed Kit endpoint is cleaner in the finished app. The implementation proceeds only with the selected transport.
