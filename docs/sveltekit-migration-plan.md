# SvelteKit migration plan

Status: implementation plan, not yet implemented. Reviewed 2026-09-12 against `main` at `c7eff5e` and the package registry. This replaces the proposed hosting architecture in the first-release handoff once implemented; the existing application and acceptance record remain the current truth until then.

## Outcome and boundaries

Run the personal pi workspace as one SvelteKit application on a loopback-bound Node process. SvelteKit owns HTML rendering, routing, request hooks, development serving, and the production build. The same process owns one pi SDK runtime, configuration service, and SSE feed. Delete the hand-written HTTP/Vite/static server. Preserve the real conversation, inspector, and side-by-side skill/settings workbench as they behave today.

This is a framework migration, not a product redesign. Keep pi's installed authentication, settings, trust, and JSONL sessions as the sources of truth; keep the pinned `@earendil-works/pi-coding-agent` 0.85.1 unless a compatibility check proves an update necessary. Do not introduce a database, hosted deployment, account system, new provider abstraction, or extra pi process. Do not edit Austin's live pi configuration during migration tests.

The current clean baseline passes `pnpm check`, all 47 tests, and `pnpm build` (2026-09-12). Existing behavior that must survive includes accepted-versus-completed command states, ordered streamed text/thinking/tool evidence, stop/steer, saved-session resume after a server restart, project trust, redaction, skill revision conflicts/undo, and project/global setting precedence.

## Stack decision

- Target the newest stable SvelteKit 2 release available when implementation begins. On 2026-09-12 the npm `latest` tag is **`@sveltejs/kit` 2.70.3**; `3.0.0-next.27` is a prerelease and is excluded. Pair it with `@sveltejs/adapter-node` 5.5.7. Recheck the stable tags and peer ranges immediately before changing the lockfile.
- Use the coherent current Vite toolchain rather than mixing majors: Vite 8.3.0, `@sveltejs/vite-plugin-svelte` 7.3.0, Svelte 5.57.0, and a compatible Vitest (currently 5.0.0). The installed Node 22.23.2 meets Vite 8's `>=22.12.0` range. Keep pnpm and commit its lockfile. Upgrade unrelated app libraries only when compatibility requires it.
- Use `adapter-node`, not `adapter-static` or a serverless adapter. The pi session is process-long and needs local filesystem/tool access. Production starts with `HOST=127.0.0.1 PORT=4317 node build`; development starts Vite/Kit explicitly on `127.0.0.1:4317` with a strict port. Preserve configurable `PORT` and the current `localhost` and `127.0.0.1` browser access.
- Retain **one** typed tRPC API for interactive queries and mutations: its existing validated router and vanilla Svelte client earn their place across the current command/configuration operations. Move that transport from `nodeHTTPRequestHandler` to the Fetch adapter inside a SvelteKit `+server.ts` route. SvelteKit form actions fit page forms, but replacing these commands would require a second validation/client contract with no user-visible gain. SvelteKit remote functions remain experimental in the current documentation. **SSE transport is an implementation choice, not a requirement to preserve tRPC subscriptions.** First try the tRPC Fetch adapter because it can keep one typed event contract; if Kit's native streamed `Response` is simpler or more reliable, use a small `+server.ts` SSE endpoint and the existing serializable event type. Keep exactly one event feed either way.
- Keep SSR **enabled** for the single workspace page and `prerender = false`. Server load supplies only a redacted, serializable initial snapshot and establishes the local session cookie; the browser hydrates the existing workspace and starts SSE on mount. Do not set `ssr = false` across the app just to carry over the old SPA. The workspace panels are in-place views of one conversation, so do not invent routes for each sidebar section or put absolute project paths into URLs.

Sources: [SvelteKit structure](https://svelte.dev/docs/kit/project-structure), [Node adapter and shutdown](https://svelte.dev/docs/kit/adapter-node), [page rendering options](https://svelte.dev/docs/kit/page-options), [server routes](https://svelte.dev/docs/kit/routing), [server hooks](https://svelte.dev/docs/kit/hooks), [server-only modules](https://svelte.dev/docs/kit/server-only-modules), [remote-function status](https://svelte.dev/docs/kit/remote-functions), [tRPC Fetch adapter](https://trpc.io/docs/server/adapters/fetch), and [tRPC SSE link](https://trpc.io/docs/client/links/httpSubscriptionLink). Version numbers above were checked with `npm view` against npm's stable tags, not inferred from older repository notes.

## Target application shape

```text
src/
  app.html                         # SvelteKit HTML template, replaces root index.html
  app.d.ts                         # App.Locals types only if hooks use locals
  hooks.server.ts                  # local request gate, headers, server init/shutdown
  routes/
    +page.server.ts               # cookie/bootstrap and redacted initial snapshot
    +page.svelte                  # workspace composition and document title
    api/bootstrap/+server.ts      # renew process cookie after a server restart
    api/events/+server.ts         # only if native Kit SSE wins the early check
    trpc/[...trpc]/+server.ts      # tRPC GET/POST via Fetch adapter; SSE if chosen
  lib/
    server/                       # pi runtime, config, router, process services, access policy
    client/                       # components, workspace controller, workbench, tRPC client
    shared/                       # serializable contracts and presentation helpers
svelte.config.js                  # adapter-node; only necessary Kit configuration
vite.config.ts                    # sveltekit() plugin and local dev host/port
tsconfig.json                     # extends generated .svelte-kit/tsconfig.json
```

Use `$lib/server` (or `.server.ts`) for runtime, config, access policy, and router; never import their values into client code. The client may use a **type-only** `AppRouter` import for tRPC inference. Keep all pi SDK objects and credentials out of load return values and browser bundles. `src/lib/shared` contains only serializable application types. Move existing UI modules with their current responsibilities; avoid a broad component rewrite during the framework cutover. SvelteKit should own the entry point, so remove `src/client/main.ts` and the manual `mount()` call. Bring global CSS and title into the page/layout in the standard Kit way.

The route layout stays deliberately small: one addressable workspace page, one RPC route, one reconnect bootstrap route, and an event route only if native SSE wins. `+page.server.ts` is a read boundary, not a place to open or switch projects. Opening a project remains an explicit validated user command. A `+layout.svelte` is optional only if a real shared layout emerges; an empty wrapper adds no value.

## Runtime and request lifecycle

1. A server-only service factory retains the testable construction of `RuntimeService` and `ConfigService`. A process-level owner caches one initialization promise and exposes `getServices()`. Initialize it once through SvelteKit's server `init` hook or an equivalent idempotent server-only bootstrap. Never create an `AgentSession` or `ModelRuntime` on every request or in a universal `load` function. This process singleton is intentional for this one-user app; it is not request/user state.
2. `hooks.server.ts` applies the local access policy before page and API handlers: require an exact loopback Host (including the configured port), reject an Origin that differs from that request's loopback origin, reject `Sec-Fetch-Site: cross-site`, and require the process cookie for RPC/SSE. Continue binding both dev and production listeners to loopback. Apply `nosniff`, `no-referrer`, and frame protection to responses using Kit's hook/configuration; do not add wildcard CORS. Do not treat a cookie alone as authorization to run a mutation. Note that adapter/Vite-served static assets may not pass through the Kit hook; they contain no private data, and the bind address still protects the listener.
3. Generate a random local token once per server process. On an accepted workspace page request, `+page.server.ts` sets a host-only `HttpOnly`, `SameSite=Strict`, `Path=/` cookie and returns `runtime.snapshot()` through the existing redacted serialization boundary. Keep the token out of the rendered page. A narrow `GET /api/bootstrap` renews that cookie for an already-open tab after a server restart; it does not open a pi session. The browser can then query `state` and resubscribe. Verify cookie behavior separately for `localhost` and `127.0.0.1`.
4. The `trpc/[...trpc]` route exports `GET` and `POST` and calls `fetchRequestHandler({ endpoint: '/trpc', req: event.request, router, createContext })`. Context receives the cached runtime/config services after the hook has authorized the request. Keep Zod input validation and existing config path/revision checks. Keep the query/mutation client on a relative same-origin URL. For events, compare the tRPC SSE subscription with a native Kit streamed `Response` against the same acceptance check; select one and delete the other. Either transport consumes the existing `events` async generator, which sends an authoritative snapshot on subscribe and then pi deltas; disconnect must propagate abort and remove its listener.
5. The page receives its initial snapshot as typed `PageData`. Build a controller instance per mounted page, seeded from that snapshot. On mount it reads recent paths from `localStorage`, fetches saved-session labels as needed, and opens the selected SSE feed. This avoids server/client HTML mismatches: do not read `localStorage`, `window`, or `document` while server-rendering; do not construct an active EventSource during SSR. Keep `crypto.randomUUID()` in submit handlers. On SSE reconnect, preserve current session/cursor guards, unsent message and workbench drafts, and the distinction between an accepted command and a completed turn.
6. Preserve pi's existing session storage and the in-memory one-active-session model. A browser refresh may rehydrate from the redacted server snapshot; a **server** restart has no active in-memory session and requires explicit open/resume of a saved pi session. Loading history must not rerun tools. Config edits remain disk writes, not live-agent changes; undo remains process-local.
7. Shut the pi runtime down once, including an active tool and SSE subscribers. `adapter-node` handles HTTP shutdown and emits `sveltekit:shutdown` for async cleanup. Register a single idempotent runtime disposer; arrange prompt cancellation on SIGINT/SIGTERM so a long-lived SSE response does not keep the local process alive until the adapter's timeout. Verify dev hot reload does not orphan a previous SDK session or accumulate signal listeners. Avoid a custom Node HTTP wrapper merely for lifecycle management.

## Migration sequence

1. **Lock the baseline.** Record current behavior and tests, check that the working tree remains clean, and create an isolated implementation branch/worktree. Inspect the current `App`, controller, workbench, runtime, config service, and HTTP tests before moving files. Do not overwrite concurrent edits.
2. **Establish a real Kit skeleton.** Use the current official SvelteKit TypeScript template in a temporary directory as a configuration reference, then adapt this repository in place. Add `@sveltejs/kit` and `adapter-node`, update the compatible Vite/Svelte/Vitest toolchain and lockfile, add `svelte.config.js` and `src/app.html`, switch to `sveltekit()` and generated TypeScript config, ignore `.svelte-kit/`, and replace `dev`, `check`, `build`, and `start` scripts. Confirm a server-rendered page from both Kit dev and `node build` before moving the pi API.
3. **Move the privileged boundary.** Put pi runtime/config/router/service ownership under `$lib/server`; add the server hook, cookie/bootstrap load and endpoint, and tRPC Fetch route. Prove one query and one mutation with a fake injected runtime in Kit dev and the built Node server. Compare tRPC SSE through the Fetch route with one native Kit SSE endpoint for initial snapshot, ordered updates, abort, reconnect, and maintenance cost. Choose one feed and prove abort removes its listener. Then delete `src/server/http.ts`, `src/server/index.ts`, and the bespoke static fallback; do not leave two app servers.
4. **Make the page idiomatic.** Replace manual client entry with `+page.svelte`, pass initial `PageData` into the workspace composition, move browser-only initialization to mount, and keep the conversation/inspector/workbench layout and navigation guards. Resolve hydration warnings deliberately rather than disabling SSR. Preserve typed router inference without bundling server values. Keep the existing real-time controller for live state; Kit load is for initial page data, not for each token/tool update.
5. **Reconcile scripts and documentation.** Replace `http.test.ts` with tests of the Kit request boundary. Adapt the test-server and browser helpers to start the Kit build with an isolated test agent directory; retain the explicitly opt-in real-provider smoke script. Update README commands/architecture, AGENTS.md's current-stack instructions, and the active implementation-handoff text in place. Mark earlier acceptance results as historical and add migration-specific evidence; remove superseded standalone-server descriptions instead of leaving two conflicting architectures.
6. **Cut over only after acceptance.** Run `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm test`, and `pnpm build`. Start the actual adapter-node output with `HOST=127.0.0.1 PORT=4317 node build` and verify the browser loop below. Commit only the migration's files and stop for Austin to dogfood; do not proceed into product hardening or deployment work.

## Acceptance checks

- The only app listener is the Kit Node server; it binds to `127.0.0.1` at the chosen port. Both `http://127.0.0.1:4317` and `http://localhost:4317` load in development and production. Another port works through `PORT` (and a matching dev command). The response is server-rendered and hydrates without console errors or duplicate pi session creation.
- Foreign Host, mismatched Origin, and cross-site requests are rejected. RPC and SSE without the local cookie return 401; an accepted page/bootstrap response issues the cookie. No credential, raw SDK session, or secret-bearing config is serialized into HTML, tRPC responses, or logs. Static assets are served by Kit/adapter, with no app-maintained filesystem routing.
- Real prompt → pi SDK → streamed text/thinking/tool args/results → transcript/inspector works. An HTTP `accepted` result is separate from final completion. Stop/steer, extension dialogs, and source/trust evidence retain current meaning. SSE disconnect/reconnect sends a fresh authoritative snapshot without replaying tools or leaking listeners.
- A page refresh preserves the active process session. A server restart rotates the cookie, leaves drafts readable, and makes the old active session stale until explicitly resumed from pi's saved history. Project switching and workbench closing still guard unsent/unsaved work.
- A saved skill revision is previewed, saved with conflict handling, and actually loaded in a fresh trusted pi session; scoped defaults do not mutate global settings unexpectedly. The manual real-provider run uses temporary settings/trust/session directories and compares Austin's actual global settings before/after without copying them into the repository.
- Desktop and half-window layouts retain the current conversation/inspector/workbench interaction. The browser bundle contains no pi SDK, Node built-ins, auth data, or server implementation values. Production startup and SIGINT/SIGTERM exit cleanly even with SSE open or a tool running.

The transport decision is intentionally narrow. A direct probe against the currently installed tRPC Fetch adapter returned `text/event-stream` and released the generator on cancellation, but it did not run through SvelteKit. The early dev-and-production Kit check decides whether tRPC SSE or a native streamed Kit endpoint is cleaner in the finished app. Record the evidence and keep the selected implementation only.
